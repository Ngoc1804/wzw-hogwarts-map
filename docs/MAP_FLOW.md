# WIZAMAP V4 — data flow on demo-5

## Scope of this branch

PH0, PH2 and PH3 are implemented in source. PH1 Entry/Preview is accepted by the user and is not repeated. PH4–PH9 architecture/prefabs/outdoor/markers/bundle and PH10 prompt migration are pending. `runtime/bundle.js`, `ui/preview.html` and the pinned production loader are deliberately unchanged; the new source is not a published V4 release.

The target flow is `Gemini MAP_DATA → normalize → resolve / Atlas blend → build → draw → markers → Preview`. For now the existing viewer/renderer consumes a derived compatibility model; when it cannot draw a scene, a minimal parchment illustration lists the supplied locations and Inspector content. This fallback is not the V4 architectural renderer.

## Public contract

`runtime/map-data.schema.json` describes MAP_DATA 4.0.0. `runtime/map-data.mjs` is the only input adapter. Recommended semantic fields:

| Field | Meaning |
| --- | --- |
| meta | RP date, time, areaName, quote. Missing date/time stays blank, never machine time. |
| mapMode | template / indoor / outdoor; omitted means automatic selection. Indoor/outdoor explicitly selects generated rendering. |
| atlasAnchor | Existing template ID, group key, canonical place ID, unambiguous source name/alias, or `custom`. |
| layoutType | Optional layout override. Gemini wins over Atlas presets. |
| pcPlace | Current PC location name; an existing local ID also resolves. |
| places[] | name, type, description, optional size and props. Local id is optional for disambiguation. |
| actors[] | name, isPC, placeName, houseOrRole, activity, observation. Optional local placeId disambiguates repeated names. |
| events[] | title, placeName, detail. Empty is valid; no event is manufactured. |

Missing/incorrect optional structures are normalized individually. A PC marker without a name is presentation-only when pcPlace was supplied. Without any PC location the fallback says the location is unknown; it does not invent a character or move NPCs to the PC. Ambiguous same-name rooms are kept unresolved rather than assigned to a random canonical room.

Legacy meta/places/actors/view/hints/customScene input is adapted at this boundary: kind and generation.function supply type; placeId references are resolved; hints become events; view.indoor.layout supplies layoutType. Legacy generation, inspector, connections, spatial and visibility data remain available and survive export. Actor placeId is retained to disambiguate repeated names. `mapSceneData` derives focus/visiblePlaceIds and the old viewer fields; these are not required from Gemini. `validateMapData` distinguishes clean input from normalized/fallback input using diagnostics; `renderable` remains true and warnings never reject the scene. `serializeMapData` escapes JSON for HTML embedding.

## Resolution

1. Explicit `atlasAnchor: custom` or legacy customScene selects Custom, including when a place resembles an Atlas name. No canon-name veto.
2. Explicit indoor/outdoor also chooses generated rendering; otherwise a requested template or known PC template owner chooses the existing fixed artwork. Missing detailed bindings are recorded as illustrative-template anchors, not a resolution exception.
3. An exact Atlas group/name/place anchor chooses its group. Empty routing-only groups follow their existing template pointer; they do not duplicate rooms.
4. For an enabled group, load its background places and merge every supplied RP place. Match identity first; an unambiguous matching background name may be replaced. RP name/type/description/props win. New RP places survive outside the original scope.
5. Layout priority is Gemini layoutType → legacy explicit layout → Atlas preset → auto. No locked-family/constraints veto.
6. A missing template/anchor/recipe resolves to the supplied scene or a neutral fallback. Unknown Outdoor is accepted as Outdoor, not rejected or relabeled Indoor.

The Atlas retains ACTIVE/LOCKED/UNBUILT source metadata. A locked group is not auto-expanded. Its explicitly supplied RP places can still produce an illustrative fallback without asserting that an approved AU map exists. Retired IDs remain migration metadata, not a renderer veto. No RP NPC/events/connections are synthesized; no data is written back to Atlas while playing.

## Atlas source

- Owner records/IDs: `maps/WZW_ATLAS_CLEAN_FINAL_REVIEW.json` (`atlas-approved-2.0`).
- Detailed approved inventory: `maps/WZW_ATLAS_APPROVED.md`.
- User's original W4.1/W4.2/W4.3 text: `maps/WZW_W4_CONTEXT.md`, preserved byte for byte.
- Derived runtime data: `runtime/atlas-index.json`, generated by `tools/build_atlas_index.py`.
- Full current inventory and provenance: `docs/V4_ATLAS_CURRENT.md`.

English aliases for 44 Hogwarts clusters and 203 room occurrences were aligned to the existing canonical records. Repeated English labels remain ambiguous outside their scope. No separate ANCHOR_MAP exists. W4 travel times, latent passages and year states are retained as Gemini context, not implemented as pathfinding or a world simulator.

## Remaining integration

Fixed display-only anchors now keep artwork when detailed bindings are missing. Remaining marker density, prefab drawing, Outdoor architecture and the final single V4 bundle are addressed in PH4–PH9. The minimal fallback prevents an old renderer failure from clearing the whole Preview during this transition. The existing production prompt still describes the old contract until PH10; do not call it the V4 prompt.
